# 欢乐三国杀技能文案审计设计

## 目标

以已解析的《欢乐三国杀》2.3.6 官方客户端配置为基准，审计 `MiNikill.js` 中 504 名武将实际拥有的技能描述。对能够唯一映射且描述由扩展自身维护的技能，将文案规则语义校准为官方版本，同时沿用仓库现有排版格式。不能可靠映射或不应由扩展覆盖的项目只进入报告，不做猜测性修改。

本次只审计技能描述，不修改技能实现。

## 审计范围

纳入：

- `MiNikill.character` 中 504 名武将直接拥有的主技能。
- 扩展在 `MiNikill.translate` 中自行维护的静态 `<skill>_info` 字符串。
- 官方 `generalcards.Cards.Card` 与 `skills.Skills.Skill` 中可建立唯一角色约束映射的技能。

不纳入自动修改：

- 武将未直接拥有的内部子技能、标记技能、卡牌说明和纯辅助技能。
- 动态翻译函数或依赖运行时状态生成的描述。
- 直接复用 noname 核心技能、且描述不由扩展维护的技能。
- 官方配置中不存在的武将或技能。
- 同名多版本且无法由所属武将唯一消歧的技能。
- 角色名称、别名或版本无法唯一映射的项目。

上述项目均进入审计报告，并记录跳过原因。

## 确定性映射

映射按以下链路执行：

```text
仓库武将
  → 仓库显示名、角色 ID 和版本前缀
  → 官方唯一武将
  → 官方武将 Skills ID 集合
  → 仓库技能中文名
  → 该武将技能集合内的官方唯一技能
```

每一步必须得到唯一结果。零个或多个候选都会终止该项目的自动修改。

角色名规范化只处理确定性的展示差异，例如仓库统一使用的“欢杀”前缀、空白和已知格式前缀。不能通过模糊相似度直接决定映射。必要的别名必须显式列入映射表，并在报告中显示依据。

技能匹配不得仅按全局中文名进行。官方配置中【无双】【仁德】【制衡】等均有多个版本，必须先由武将的 `Skills` 字段缩小候选范围。

## 文案规范化与修改

官方 `Describe` 是规则语义基准。写回仓库前只允许以下格式规范化：

- 将 `<br>` 转为仓库使用的连续句子或编号分段。
- 统一全角中文标点、引号和括号。
- 将纯排版用阿拉伯序号转换为仓库现有的 `①②③` 风格。
- 删除官方配置中的多余空格。
- 保留技能名、时机、条件、次数、区域、数值、选项、例外和变量定义的完整语义。

不得自行润色、概括或补充官方未写明的规则。若格式规范化可能改变句法范围，该项转为人工报告，不自动修改。

只修改普通单引号、双引号或模板中不含表达式的静态 `_info` 文本。动态模板和运行时描述不自动改写。

## 审计产物

审计产生机器可读结果和人工摘要，每个实际技能包含：

- 仓库武将 ID 与显示名。
- 仓库技能 ID 与显示名。
- 官方武将 ID、技能 ID。
- 当前描述、官方描述和规范化官方描述。
- 状态：一致、需修改、核心复用、动态描述、缺少映射、映射歧义或缺少本地描述。
- 映射依据和跳过原因。

报告保存在会话 artifact 目录，不提交官方客户端数据或大批生成文件到仓库。仓库只提交经核验的文案修改、必要的轻量审计脚本或测试，以及设计/计划文档。

## 验证

实施采用以下验证门槛：

1. 先运行审计并保存基线结果。
2. 对“唯一映射且扩展自有”的差异逐项生成修改。
3. 再次运行审计；所有可自动处理项目必须为一致。
4. 确认修改仅触及对应 `_info` 文本，不修改技能逻辑。
5. 运行 `node --check js\precontent\MiNikill.js`。
6. 运行 `git diff --check`。
7. 人工抽查数值、次数、条件、变量定义和括号作用域差异。

最终结果必须明确报告已核对数量、修改数量、一致数量及各类未自动处理数量，不能将未映射项目描述为“已与官方一致”。

## 风险控制

- 官方配置版本为 2.3.6；配置中缺失的后续武将只报告，不外推。
- 同名技能必须依赖所属武将消歧，禁止全局替换。
- 扩展复用的 noname 核心技能不覆盖全局翻译，避免影响扩展外武将。
- 文案审计不代表技能实现一致；运行逻辑审计需另立任务。
- 官方配置及解析产物保留在会话存储，不提交受版权保护的客户端数据。
